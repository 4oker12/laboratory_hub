# Archer C64 V1.0 — evidence from physical-device HAR (2026-11-09)

## Evidence and provenance
Local user-supplied `wife(1).har` (52 HTTP entries), plus accompanying vendor JavaScript libraries.
**The raw HAR is private and MUST NOT be committed**: it includes a password-derived
`?code=7&...&id=...` field and session/token-related response fields.
This report intentionally excludes raw URLs with query values, cookies,
credentials, session tokens, request secrets, encryption keys and response bodies.

### Device — confirmed, not inferred from manual selection
- Stock interface hostname: local private `192.168.0.1`.
- `modelName`: **Archer C64**
- `hardVer`: **Archer C64 1.0**
- `softVer`: **1.13.2 Build 230824 Rel.74702n(4555)**
- Physical hardware: **V1.0**.
- Hardware revision and build were absent in the earlier passive RouterLab report because
  the pre-login page did not expose them in the fields being examined.

This read operation is the only active C64 request enabled in the pilot. It is
explicitly user-triggered, private-IP and same-origin only, and parses an allowlist.
No automatic probing of unknown routers or other brands is performed.

### Firmware and login module evidence
- `/config/models.json` advertises `firmwareModel`, `localLoginControl`,
  `tpLoginControl`, `wirelessBasicM`, `wirelessBasicM5g`.
- `/config/device.json` includes `gdprSupport: true`; this is a build
  configuration flag, not a proof that the runtime has completed a crypto exchange.
- `/modules/login/localLogin/models.js` configures `localLoginProxy`
  with `MERProxy`. The authentication path uses `?code=HTTP_AUTH&asyn=0&id=...`.
- `/modules/login/localLogin/controllers.js` calls `getLocalTmpKey()`,
  `resetEncryptor(...)`, `main.login(...)`, then `syncEncryptor()`.
- `/modules/main/models.js` configures `gdprProxy`:
  `?code=16&asyn=0`, with `get`, `enable`, and `set` operations.
- `/modules/main/main.js` defines temporary-key handling, token generation/
  storage, login retry and post-auth encryption synchronisation.
- `/js/libs/tpEncrypt.new.js` and `/js/libs/cryptoJS.min.js`
  implement the stock crypto primitives.
- `/js/app/url.js` appends a session query parameter named `id` to vendor requests.

**Important:** The HAR contains HTTP 401 responses for `HTTP_AUTH` calls
and NO confirmed successful login-to-authenticated-session-to-readback sequence.
It does not prove credentials, sequence establishment, encrypted POST framing,
session persistence, WAN SET or Wi-Fi SET. No write operations should be inferred.

### Next physical validation
1. Install the unsigned iOS app after local signing.
2. On the C64 login page choose C64 (if not auto-detected).
3. Tap **Прочитать модель и прошивку**, then **Скопировать диагностику**.
4. Expect `c64Readback.ok=true`, `hardware=V1.0`, `build=230824`,
   and `loginVerified=false`, `writesEnabled=false`.
5. If the read fails, copy sanitized `c64Readback.reason`; do not export another raw HAR.

The validated read-only device-block mechanism is a candidate for a
**family-scoped MERProxy identity reader**, but MUST NOT be generalized to
TP-Link models without independent HTTP evidence.
